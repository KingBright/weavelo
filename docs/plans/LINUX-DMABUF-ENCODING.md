# Linux GPU 原始帧到 HEVC 的直接通路

2026-11-03，用户已回复“按方案继续”，具体实现已获批准。共享 GPU 帧与直接编码基础已实现并验证；PipeWire 租约 / 协商仍待接入，尚未切换默认采集路径。

## 已验证的起点

主分支 `4cbe48d` 已正式安装到 HO5。现有路径为 PipeWire 的
MemFd / MemPtr → 有界 owned 原始帧 → VAAPI 上传与 GPU 缩放 → HEVC。
已经去掉 FFmpeg 原始像素子进程管道及 Annex-B 等待下一帧的延迟，并复用无人引用的原始平面。

两路同时传送真实桌面，播放 1080p 动态图案，预热后观测 30.006 秒：

| 接收方 | 帧数 | 总耗时均值 | 硬编均值 | 拷贝与排队 | 上传 / VPP | 超过 20 ms |
| --- | --- | --- | --- | --- | --- | --- |
| 努比亚 | 1429 | 10.824 ms | 7.060 ms | 1.768 ms | 1.988 ms | 1 帧 |
| MacBook | 1429 | 11.403 ms | 7.636 ms | 1.776 ms | 1.984 ms | 1 帧 |

发送错误为零。完整证据位于 HO5 本轮任务目录的
`native92-linux-real-motion-threshold-{samples,result}.json`。
当前尚未满足正常 10 ms 内和 20 ms 上限，不能用硬编时间替代总耗时。
HO5 的 VAAPI 低功耗入口实际不可用；不以降低画质满足耗时指标。

## 具体实现

1. 在现有受限 PipeWire FD / 节点上协商 DMA-BUF。继续使用已经获得的
   portal 授权和持久恢复流程，不连接默认 PipeWire 实例寻找其它源，不修改系统授权。
2. 原始帧边界同时承载现有 CPU 平面和 GPU 平面租约。共用来源代际、时钟、
   crop / transform、颜色、最新原始帧邮箱、输入与会话逻辑；不用新增网络协议。
   GPU 描述保留实际 fourcc、modifier、平面 FD、offset、stride 和尺寸，并逐项校验。
3. PipeWire 对象与借出的 buffer 继续由原生工作线程持有；跨线程只传
   有界、可取消的租约与归还消息。最后一个消费者完成后才归还原始 buffer，
   防止生产者在编码器读取期间改写像素；旧来源的归还不得进入新代际。
4. 在当前 FFmpeg 8 / VAAPI 桥中把 DRM PRIME 帧直接导入同一 GPU，使用现有
   GPU VPP 转色 / 缩放和 HEVC 参数。请求直接映射并检查真实结果；不把隐式 CPU
   下载、转换或上传称为零拷贝。保留 modifier、同步与 GPU 完成时序。
5. 实际只提供 MemFd / MemPtr 的来源继续使用已经工作的 owned 帧适配器，
   共用同一个后续编码与校验入口；这属于平台能力差异，不新增旧客户端协议分支。
   实际路径与不可用原因进入本地诊断。
6. 继续只替换未编码的旧原始帧；编码后的参考帧与关键帧有序发送。
   原始帧、FD、GPU surface 与归还队列均有界。暂停、结束、拒绝和权限撤销
   释放租约；清理未完成时如实保留待完成状态，不假报已经回收。

## 验证与交付

- 覆盖平面布局、越界、代际、保留中的别名、取消和迟到归还；真实硬件验证导入及 GPU 完成，
  不以文件描述符存在或解码提交当作实际呈现。
- 逐组核对实际解码像素和 SPS 颜色；原有捕获、码率与质量参数保持一致。
- 核对屏幕 / 窗口、crop、旋转、DPI 和 pointer 逆变换；不因缓冲类型改变坐标。
- 用相同双路动态负载对照总耗时及超过 10 / 20 ms 的帧数；目标正常低于 10 ms，
  稳态观测窗口中没有超过 20 ms 的帧，另列初始化和异常负载。
- 原生 FD / surface 数量与 RSS 在反复开启、停止后有界；检查结束和权限撤销的实际清理。
- 仅使用各机现有 main checkout、缓存、构建和安装入口。先在 HO5 验证，
  再按当前协议向其它自有设备验收收流；不改签名、设备身份、凭据或认证。

这次新增原生 GPU 采集 / 导入路径，属于 AGENTS.md 要求先确认具体方案的范围。
日常修复、已有路径优化、构建、发布和兼容更新继续按既有授权直接执行。


## 基础实现验证（2026-11-03）

共享帧增加有界 DRM 描述和最后持有者归还回调；CPU 平面继续使用既有路径。
本地 FFmpeg / VAAPI 桥新增直接导入、GPU VPP、完成同步及 C 侧引用保留；未接入 PipeWire 协商，当前产品仍使用 CPU 原始平面适配器。
HO5 用真实 DMA-BUF 完成裁剪与颜色对照：从 640×360 的 BGRA 缓冲裁剪 `(96,40,400,240)`，
GPU 与原 CPU 路径的独立解码像素完全相同；与生成的 RGB 参考图内部区域平均误差 1.238。
SPS 均为 400×240、TV range、BT.709 / IEC61966-2-1 / BT.709。
四帧及一个无效布局的返回回调恰好五次；没有在导入前将 DMA-BUF 当作 CPU 字节切片。
这些小尺寸合成测试不代表 4K 实机性能目标已达成。

现有 Linux SDK 缺少 libva 头文件，已从[官方 2.24.1 发布源码](https://github.com/intel/libva/releases/tag/2.24.1)
补入既有 SDK；复用系统已有 `libva.so.2`，未安装或替换系统运行库。
