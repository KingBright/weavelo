# 统一共享权限与双向多窗口

2026-10-31，依据用户本次要求。用户已明确回复“按此方案继续”，确认下文原生授权生命周期与投送协议的具体实现。普通修复、构建、发布和兼容升级继续自动执行。

## 同一个入口

所有平台在设备页提供“共享与权限”，Android 原 Sharing 页使用同名入口。卡片只保留一句说明：“选择可共享的画面，并设置控制与音频权限。”

每项仅显示名称、实际状态和一个操作：屏幕/应用窗口、远程控制、音频；Android 增加后台通知。操作按平台调用真实系统入口：macOS 录屏和辅助功能设置，Windows 实际可用性和适用的隐私设置，Linux 系统屏幕/窗口选择器，Android MediaProjection、无障碍和音频权限。没有独立系统许可的能力显示实际可用状态，不虚构“已授权”。拒绝、撤销、系统不支持和等待本人确认均显示真实结果；设备在线不代表已经共享。

Linux 不再要求先收到视频订阅才能授权，也不使用“Refresh viewers”作为主要操作。GUI 经现有同用户私有 IPC 请求后台服务打开系统选择器；后台持有真实 portal/PipeWire 资源，关闭 GUI 不停止已经共享的来源。取消请求、切换设备网络和退出整个 App 都释放对应资源。IPC 不传递原始授权令牌或文件描述符，不启动第二套网络运行时。

## 一次选择与恢复

Linux 提供“记住这次选择”。在系统支持时请求 persist_mode=2，按当前系统用户、Weavelo 应用和已配对设备网络保存系统返回的恢复令牌；使用现有私有配置目录和原子写入，不进入日志、网络、同步目录或 IPC。令牌每次恢复后更新，系统撤销、来源消失或恢复失败时显示“需要重新选择”。同一来源可供多条独立订阅使用；关闭一个观看窗口只释放该订阅，停止共享才撤销父级系统授权。系统仍可能要求重新确认，不能把请求永久许可说成永久保证。

macOS/Windows/Android 使用系统实际支持的持久许可。Android 普通投屏的每次新 MediaProjection 会话仍由本人确认；不借此启用已暂缓的 USB 托管采集方案，不代替本人批准系统授权，不修改 TCC、AppOps 或安全策略。

## 投送与拉取对等

两种发起方式共用来源选择、订阅和观看窗口：选择整屏、一个应用窗口或多个应用窗口，再连接或投送。每个来源独立窗口、源版本、输入租约、停止和错误状态；来源变化取消旧手势并释放旧按键。一个来源结束不关闭其余窗口或文件传输。电脑窗口明确显示设备与应用图标/名称，并提供本地全屏、恢复和最小化；手机以同一会话模型提供分屏/切换和触摸输入。

现有 DeliveryOffer 增加有界、去重的 sources: Vec<CaptureSource>（1–8 项）；同一组 sources 绑定现有本地投送 ticket，续约不能偷偷改来源，修改选择需重新发起。接收端先检查自身可接收数量，再逐项使用现有认证连接、Subscribe/SourceInput 和原生媒体管线。来源校验在发送端再次执行，越界、无权限或失效来源有明确结果；不把 ticket 当作设备身份。自有设备统一升级当前协议，不保留旧协议兼容分支。

“多窗口”指多个独立来源，不能用多个相同整屏窗口充数。当前 Windows 窗口采集/输入和 Android 投送接收尚有实现缺口，逐项补齐。Android 单次系统投屏目前只能选择系统实际允许的整屏或一个应用；多路接收与同时采集多个 Android 应用是两种能力，不能承诺系统没有提供的后者。界面如实显示能力，后续新增采集后端另行明确。

## 性能与验收

复用共享会话、来源校验、几何与手势；平台保留原生采集、硬件编解码、GPU 呈现和系统输入。共享来源扇出保留原生缓冲和每订阅生命周期，不引入 CPU 全帧转色或中继重编码。测量启动可见时间、帧间隔、输入延迟、CPU/GPU、内存和带宽；解码/提交不等于实际呈现。

先修复 Linux GUI→后台授权和首个来源，再验证授权恢复与独立多订阅释放；各平台统一权限入口与状态后，补齐多来源投送/拉取和手机收发。按四台电脑及两部手机逐方向记录真实画面、单窗口/多窗口、独立停止、控制/音频、撤销/重连、DPI/旋转/键盘开合和 UU 嵌套远控。用户不在设备前时保留本人授权与物理验收为待完成，不拿列表、构建或两个 Mac 的结果代替全设备完成。
