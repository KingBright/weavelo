# 自适应窗口清晰度与可视区域串流

2026-11-04 制定，2026-11-05 用户明确回复“按方案继续实现”。用户要求：独立应用按真实窗口像素提高文字清晰度；手机放大后优先传输可见局部；支持随时缩小、放大和拖动。以下原生媒体与协议方案已获确认；实施与实机验收进展单独记录，不将方案批准等同于功能完成。

## 产品行为

- 默认自动清晰度，复用现有会话画质设置。用户指定的码率和分辨率上限继续有效，不新增全局控制面板或手动 ROI 开关。
- 独立应用以该窗口的实际像素尺寸为依据，区分逻辑点、物理像素和显示缩放。保留宽高比；带宽允许时接近原生像素采集和编码，文字优先。超过源像素的放大不称作新增真实细节，不引入 AI 超分或截图/JPEG 轮询。
- 放大时将可见区域加少量缓冲边界作为编码区域；缩小后自动扩大源区域，回到全图时恢复全图串流。不是同时长期传输全尺寸全图与高清局部两路。
- 触摸、鼠标、窗口改大小、横竖屏、Fit/Fill 和输入法遮挡均使用同一套可见几何。主动投送与被动拉取、桌面与手机共用需求和状态算法。

## 当前代码事实

`protocol/src/session.rs` 的 `SubscriptionRequest` / `Configure` 只有整体宽、高、FPS 和码率，没有远端 ROI。`host/src/capture.rs` 用 `fit_capture_size` 配置 ScreenCaptureKit；窗口采用 Best capture resolution，但目标尺寸仍须核对真实 backing pixels。Android `RemoteVideoSurface.kt` 当前通过 GPU `graphicsLayer` 在本地缩放、平移，远端仍编码完整来源。Linux `host/native/linux_encode.c` 已用 VAAPI 帧 crop rectangle 处理原生可见几何，可复用现有 GPU 裁剪能力；这些事实不等于已完成动态 ROI。

## 连续手势的处理

1. 本地 GPU 每次手势立即更新显示，不等待网络确认。一次双指缩放/视图平移开始时，沿用现有手势取消规则释放远端按键/拖拽，不把导航手势作为远端点击发送。
2. 从真实 viewport、当前缩放和平移逆算完整来源中的可见矩形；合入旋转、镜像、黑边、DPI、Fit/Fill、键盘遮挡。可见源区域始终裁在实际来源范围内。
3. 首次离开已传区域立即请求；连续更新只保留最新未处理需求，起始合并间隔 50 ms（最多约 20 次/秒）。来源或会话改变时取消旧需求。只合并需求、过期原始帧和已解码输出，不随意丢压缩参考帧。
4. 编码区域比可见区域每边约多 10% 的边界，并按拖动方向作有界预取；以真实带宽和编码预算限制总面积。边界内移动无需重配；即将越界时提前移动裁剪框。该参数是起始实测值，不是固定性能承诺。
5. 平移保持编码输出尺寸不变，只更新原生 GPU 裁剪矩形，不因每次手势重启采集、编码器或强制关键帧。
6. 缩放改变可见源面积，但输出像素仍围绕接收屏幕实际像素和源像素上限选取。仅跨越分辨率档位后改变编码尺寸；用约 150 ms 的手势稳定窗口及约 400 ms 的档位滞回抑制抖动。快速缩小超出覆盖范围时优先恢复覆盖，不等待稳定窗口。
7. 新区域尚未到达时使用现有已知画面作本地预览；已传区域之外不拉伸伪造像素、不按未知几何注入输入。全图缓存只作短暂导航参考，不冒充新区域的实时清晰帧。

## 公共协议与帧归属

- 沿用当前已认证连接、来源标识、独立订阅与所有者；统一升级当前会话协议，不保留旧协议兼容分支。具体新版本由当前源码版本递增。
- 增加有界 `ViewportDemand`：订阅 ID、来源修订、递增需求修订、完整来源中的归一化可见矩形、接收端物理 viewport 尺寸、自动/手动质量限制。拒绝 NaN、越界、空矩形、失效来源、错订阅和倒序需求。不能通过 ROI 请求改为桌面或另一个应用。
- 来源端回复实际采用的完整源像素尺寸、裁剪矩形、编码可见尺寸和几何修订。实际矩形遵守 NV12/硬件编码对齐约束；不能直接把请求矩形当成已经生效的矩形。
- 每帧携带/绑定它实际采用的几何修订；采集、GPU 裁剪、编码、网络、解码和展示保留这一归属。几何描述与帧可关联重发，缺失描述的帧不得按最新几何猜测呈现。元数据表有界，随实际帧所有权回收。
- 展示端按正在显示的那一帧，将局部坐标逆变换为完整来源的归一化坐标，再交给既有输入通道和平台适配器。避免同时维护一套独立鼠标坐标算法；不要求为每次平移重新授予键鼠绑定。
- 只有编码尺寸、颜色元数据、真实来源等必须重建时才建立新媒体代次并请求关键帧；先失效旧几何输入，迟到帧不混入新来源。不能为了新鲜度破坏 HEVC 参考链。

## 清晰度和负载策略

公共策略根据源像素、目标物理像素、实际吞吐、队列延迟和既有网络统计选择分辨率/码率；不把固定 1080p 或固定码率用于所有窗口。小区域可在较少像素总量下保留更高文字清晰度；只在真实带宽余量下提高质量。负载过高先降低不必要的更新频率/分辨率档位，保持有界延迟，不排队等待过期 viewport，也不改变用户手动上限。

同一来源共享原生采集；只有 ROI、输出尺寸和编码参数相同的观看需求共享编码。不同用户的可视区域互不覆盖；停止一个订阅只释放它自己的需求和资源。不存在为了共享逻辑强行全帧读回 CPU 的路径。

## 原生适配

| 平台 | 实现原则 |
| --- | --- |
| macOS | 核对 ScreenCaptureKit 的窗口像素比例；优先利用已存在的原生源/IOSurface，在受支持的 SCK 裁剪或 Metal GPU 裁剪后送 VideoToolbox。平移不重建 SCK 会话，保留实际色彩信息。 |
| Windows | 保持 WGC / D3D11 资源和 GPU HEVC 编码；用 D3D11 原生裁剪/缩放适配，禁止回退为 GDI 截图或 CPU 全帧转色。 |
| Linux | 复用 PipeWire DMA-BUF、实际源 crop geometry 和 VAAPI VPP；按帧更新裁剪矩形，尺寸档位变化时才重建必要资源。X11 原有受支持路径单独核对，不把 Wayland 结果冒充全部 Linux。 |
| Android | 接收端复用现有 Surface 解码和 viewport 手势；手机作为屏幕来源时，MediaProjection 纹理经 EGL/OES 原生 GPU 裁剪送 MediaCodec Surface。保留真实系统授权，不启用暂缓的 USB 采集。 |

该功能首先覆盖屏幕和应用窗口。摄像头的光学/数字变焦、传感器裁剪与前后摄切换属于不同需求，不在本次隐式变更摄像头来源语义。

## 实施次序与验收

1. 先修正/验证独立窗口的实际像素尺寸和自动质量需求，建立清晰文字、带宽与编码耗时基线；不先添加第二路高清流。
2. 公共几何、需求合并和帧归属；Mac 来源 → Android 查看端先闭环，覆盖手势立即响应与单应用真实输入。
3. 补齐 Windows、Linux 与 Android 作为来源的原生裁剪，统一升级所有自有客户端。未接入的平台明确记录，不宣称全部完成。
4. 用自有测试应用的细文字、线条和坐标标记验收：1×↔4×反复缩放、持续平移至四角、快速反向、变更窗口尺寸、横竖屏、键盘弹出/收起、断网恢复、源切换、多观看者、独立结束。
5. 独立记录真正可见画面、目标端输入坐标、源尺寸/实际 ROI/编码尺寸、区域更新耗时、有效码率、FPS、编码 P95/P99、CPU/GPU、内存和参考链错误。Linux 继续以正常约 10 ms、无超过 20 ms 为实测目标，不拿历史 101 数据替代。

普通检查、main 单 worktree 提交推送、正式签名打包和兼容升级继续自动执行。此方案新增原生媒体与协议能力，因此按仓库 AGENTS.md 的明确约定取得一次具体方案确认；不添加依赖锁、补丁哈希审批、人工升级门槛或额外版本回退流程。


## 实施进度（2026-11-05）

公共需求／逐帧几何、四个平台的原生来源裁剪、共享采集与接收端代码已接入。Mac、Windows、Linux 和两部 Android 的 GPU 部件检查通过；桌面查看端共用视图几何，支持立即本地缩放／平移、最新区域合并，以及与实际绘制帧一致的输入坐标。桌面普通滚动继续发给远端；“Move view”显式切换为本地导航。GPUI 当前未提供原生捏合事件，桌面通过会话显示面板与本地导航滚轮缩放。详细事实见 [GUI 进展](../testing/2026-11-02-GUI-PROGRESS.md)。

新功能尚未统一打包／升级，不能将原生部件与测试界面验收当作所有设备的真实显示验收。仍需各平台产品构建、已签名 SCK 共享采集、普通手机系统屏幕授权、连续手势／输入／旋转与完整设备矩阵。Linux 小区域冷启动曾测得 41.748 ms，仍未达到用户不超过 20 ms 的目标；满分辨率性能继续实测。

## 局域网延迟验收（2026-11-05 补充）

用户提出 WiFi → WiFi 下约 25 ms 的目标。将它作为待实测的端到端优化目标，分别记录网络 RTT、采集等待、GPU 裁剪、编码、传输、解码、呈现等待和真实可见画面；不能以其中一项代替完整延迟。记录设备、连接路径（直连或中继）、分辨率、FPS、刷新率、样本量与 P50/P95/P99。源码时间戳必须保持原始采集归属，静止帧因新 ROI 重编码也不伪造新采集时间。实际显示使用独立拍摄或可核对的源/接收画面观测，编解码提交时间不能作为显示时间。

优先消除排队、原始像素读回和额外同步等待，保留正确颜色、参考帧链、图像质量和输入。不同设备是否稳定达到目标仍需实机验证，不承诺所有 WiFi 环境均为 25 ms。可参考 [Moonlight 统计口径](https://github.com/moonlight-stream/moonlight-docs/wiki/Frequently-Asked-Questions) 对呈现等待和网络波动的区分，以及 [NVIDIA 官方低延迟编码建议](https://docs.nvidia.com/video-technologies/video-codec-sdk/13.1/ffmpeg-with-nvidia-gpu/index.html)。


Windows 已验证静止窗口、双观看者共享采集、独立区域与独立结束。两部 Android 已验证独立 GPU 区域编码；这些结果仍是部件检查，当前协议的全产品交付与实机矩阵尚未完成。


## 自适应会话外框（2026-11-07 用户补充）

手机整屏、手机独立应用和电脑独立应用增加“适配画面”模式。开启时按来源完整画面的宽高比调整本地窗口外框，适应远端横竖屏及应用窗口尺寸变化，并约束在当前本地显示器的可用空间内。以完整来源几何为依据，不能随编码降采样或用户缩放后的 ROI 反复缩放外框。

用户手动改变外框尺寸后保留其选择，停止自动跟随；仅移动窗口不退出自动模式。操作栏提供一个紧凑的“适配画面”按钮，一键恢复自动适配。全屏或最大化期间不抢改外框。设备管理窗口不受此模式影响。

Android 独立应用的旋转必须同步应用布局、采集表面、编码输出、逐帧几何版本和输入几何；不能只在接收端旋转纹理冒充应用横屏。采集几何变化（包括尺寸不变的反向旋转）撤销旧输入租约并拒绝旧几何编码帧；客户端须报告实际绘制的新几何版本才能重新获得输入。仅调整同一采集几何下的 ROI 不撤销输入。来源切换仍使用独立的来源版本。该请求字段使用会话协议 11，自有设备统一升级，不增加旧协议兼容分支。

验收涵盖纵向→视频横屏→纵向、旋转前按住的触摸和按键取消、旋转后四角点击，以及手动外框尺寸保持和按钮恢复。这里记录需求与实现决策，实际交付状态另见设备验收记录。
