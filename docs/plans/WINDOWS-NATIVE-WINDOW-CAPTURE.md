# Windows 原生屏幕与窗口采集

2026-10-31。用户已回复“按此方案继续”，确认下列 WGC 与硬件编码方案；普通修复及已授权发布继续。

当前 cube 安装的 FFmpeg 9.0.1 已包含 `gfxcapture`，实际 AMD Radeon 8060S 的 `hevc_amf` 已完成六帧合成画面编码。现有产品仍走 `gdigrab + libx265`，且没有独立应用窗口来源；这两项都没有满足原生性能与双向多窗口目标。

实现范围：

- 沿用现有私有 FFmpeg 包、认证会话、HEVC 传输、独立订阅和原生观看管线；Windows 采集改为 Windows.Graphics.Capture，输出 D3D11 硬件帧，cube 使用 AMF 硬件 HEVC 编码。其他显卡按实际硬件能力使用对应原生编码器；不以 CPU 下载、全帧转色或 GDI 兼容分支冒充完成。
- 同一个来源目录列出真实显示器和应用窗口。现有 `Window(u32)` 使用进程内不复用的来源 ID，解析到完整 HWND、所属进程身份与窗口生命周期；不截断 64 位句柄，不按标题模糊选择。窗口关闭或句柄复用结束原来源，不把后来的窗口接到旧订阅上。每个来源可独立投送、拉取、停止，保留真实图标。
- 视频和输入使用实际采集内容矩形及同一逆变换。移动、调整大小、DPI 或来源变化时取消旧手势和按键，发布新几何后再接受对应输入。显示器、窗口边框和客户区不能混算；窗口最小化、不可用或受系统保护时如实反馈。
- 保留实际颜色信息；检查源显示器、GPU 输出格式和 HEVC SPS，不把未知颜色声明为 sRGB。尺寸变化重建对应编码代次，保持宽高比。系统限制或缺少硬件能力返回明确原因，不悄悄改变系统显示、安全或授权设置。
- 共用现有订阅、输入所有权、文件和音频生命周期。窗口采集、图形资源与硬件编码仅放在 Windows 平台适配层，不复制会话或传输逻辑。

验收顺序：先编译与来源/几何/生命周期检查，再用自有合成窗口验证真实接收画面、两个不同窗口并行、独立关闭、移动/缩放/DPI 和控制；最后验证四台电脑及 Android 接收。记录启动可见时间、接收帧间隔、CPU/GPU、内存与带宽；没有真实采集时间戳时，不把编码输出时间称为采集延迟。合成编码成功只证明硬件编码器可用，不代表 WGC、GPU 互操作或产品链路已通过。

依据：[FFmpeg gfxcapture](https://ffmpeg.org/ffmpeg-filters.html#gfxcapture) 定义 D3D11 输出、原生句柄、尺寸及来源消失行为；[Microsoft 屏幕采集](https://learn.microsoft.com/en-us/windows/apps/develop/media-authoring-processing/screen-capture) 定义系统能力、选择及颜色限制。以当前安装版本实际支持的参数为准。
